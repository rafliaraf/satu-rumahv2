# Anti-Slop Audit 001

- Date: 2026-09-07
- Mode: AFTER
- Scope: Flutter UI in `lib/`, with emphasis on the Admin, Developer, and Perwaskim role shells and the existing submission/monitoring flows.
- Companion skill: `antislop-ui` was applied together with the core rules.
- Status: audit only. No Flutter source has been modified. Per Mode 2, fixes wait until the user approves specific finding numbers.

## Findings

### AS-001 - HIGH - Plausible operational data is fabricated or demo-only without a consistent visible disclosure

- Rules: R-17, R-38, C-5.
- Evidence: `lib/features/pengajuan/presentation/providers/pengajuan_form_controller.dart:220-325` seeds a static in-memory repository with project IDs, dates, unit counts, companies, and statuses. `lib/features/dashboard/presentation/screens/tab_beranda_admin.dart:66-100,127-225,274-301` presents counts, project names, a `35%` progress value, `2 hari lagi`, and `24` as operational dashboard content. `lib/features/dashboard/presentation/screens/tab_beranda.dart:37-70,164-166,272` generates dummy submissions and a maintenance date. `lib/features/notifikasi/presentation/providers/notifikasi_provider.dart:6-42` seeds realistic notification events.
- Why it is slop: the Developer screen exposes a Demo Cepat control, but Admin and Perwaskim surfaces present similar values as if they were live. The user cannot reliably distinguish product truth from prototype fixtures.
- Fix proposal: keep fixtures only behind an explicit demo mode with a persistent visible label, or replace them with honest empty states until a real source exists. Remove random IDs and unsourced operational numbers from the default role homes.

### AS-002 - HIGH - Remote sample photographs are used as if they were project evidence

- Rules: R-23, R-38, C-5.
- Evidence: `lib/features/pengajuan/presentation/screens/pengajuan_admin_list_screen.dart:22-27` defines three Unsplash URLs as `sampleImages`, and `:168-170` assigns them to real-looking application rows by index.
- Why it is slop: external stock photos are not tied to the project records and are not labeled as placeholders. They make a prototype row look like verified housing evidence.
- Fix proposal: use an honest neutral placeholder with visible copy such as `Foto proyek belum tersedia`, or load only project-owned media. If sample imagery is retained for a demo, label the whole environment and the image treatment as sample data.

### AS-003 - HIGH - User-facing copy contains forbidden em dashes

- Rule: R-02.
- Evidence: `lib/features/monitoring/presentation/screens/laporan_preview_screen.dart:642` contains `Email — Belum tersedia`, and `:677` contains `Arsip Sistem — Belum tersedia`.
- Why it is slop: the copy violates the core copy gate and makes the interface inconsistent with the required punctuation policy.
- Fix proposal: replace the em dash with a colon or parentheses, for example `Email: Belum tersedia`.

### AS-004 - HIGH - Data screens do not expose complete empty, loading, and error states

- Rule: R-27.
- Evidence: `lib/features/dashboard/presentation/providers/admin_dashboard_provider.dart:27-75` is a synchronous in-memory provider, while `lib/features/dashboard/presentation/screens/tab_beranda_admin.dart:57-102,122-231` always renders metric and action cards without loading, error, or empty branches. `lib/features/monitoring/presentation/widgets/tab_beranda_monitoring.dart:222-227` silently returns `SizedBox.shrink()` when active assignments are empty. `lib/features/dashboard/presentation/screens/tab_beranda.dart:175-182,288-312` has an empty submission branch but no loading or error branch.
- Why it is slop: the ideal populated state is designed, but the user receives no explanation or next action when a role has no data or a data source fails.
- Fix proposal: define a shared role-home data-state contract with explicit loading, error/retry, empty, and populated variants. Replace silent omission with a useful empty message and one next action.
### AS-005 - HIGH - A visible shortcut points to a non-existent feature without a clear unavailable label

- Rules: R-24, R-26.
- Evidence: `lib/features/dashboard/presentation/screens/tab_beranda.dart:19-31` maps `Format Dokumen` to `null`; `:234-252` still renders it as a normal shortcut card; `lib/core/widgets/route_feedback.dart:84-92` only shows a snackbar after the tap.
- Why it is slop: the card has the visual affordance of a finished destination, but it cannot navigate anywhere. A temporary snackbar is not the same as a clearly labeled `Coming soon` control.
- Fix proposal: remove the shortcut until a real route exists, or render a disabled/coming-soon state with visible copy and a clear reason. Keep the placeholder behavior explicit in source.

### AS-006 - HIGH - Muted text tokens fail or risk failing WCAG AA contrast on light surfaces

- Rule: R-25.
- Evidence: `lib/features/dashboard/presentation/screens/dashboard_screen.dart:35-36` uses `AppColors.grey500` for unselected navigation on white; `AppColors.grey500` (#9E9E9E) against white is approximately 2.68:1. `lib/core/theme/app_theme.dart:80-105` uses `AppColors.grey400` (#BDBDBD) as normal input hint text on `AppColors.grey50`; that pairing is approximately 1.88:1. Similar grey500 hint/label usage appears at `lib/features/auth/presentation/screens/login_screen.dart:202`, `lib/features/onboarding/presentation/screens/onboarding_screen.dart:66`, and `lib/features/pengajuan/presentation/screens/pengajuan_admin_list_screen.dart:84`.
- Why it is slop: the interface uses a neutral color hierarchy without checking the actual contrast of text roles, so secondary copy can become unreadable while still looking intentionally muted.
- Fix proposal: define a contrast-tested `textMuted` token for normal text, reserve lighter greys for non-text decoration only, and verify each text/background pairing at 4.5:1 or above.

### AS-007 - MEDIUM - Literal emoji are scattered through UI copy and notification titles

- Rules: R-04 and `antislop-ui` Emoji as Decoration.
- Evidence: `lib/features/dashboard/presentation/screens/tab_beranda_admin.dart:42` uses `👋`; `lib/features/dashboard/presentation/screens/tab_beranda.dart:68` uses `✅` in a notification title; `lib/features/pengajuan/presentation/providers/pengajuan_verifikasi_controller.dart:617` uses `📍`; `lib/features/monitoring/presentation/providers/monitoring_form_provider.dart:361,363` uses `📝` and `🔓`; `lib/features/pengajuan/presentation/screens/pengajuan_success_screen.dart:113` uses `🔔` in a button label.
- Why it is slop: emoji add a second, platform-dependent visual language to an otherwise Material/Rustic Authority UI and do not provide accessible semantic meaning by themselves.
- Fix proposal: remove the emoji from copy. When a visual mark is necessary, use a relevant Material icon with a semantic label and a documented reason, or let the text carry the meaning.

### AS-008 - MEDIUM - Palette and accent semantics drift away from the declared Rustic Authority system

- Rules: R-01, R-29, R-31.
- Evidence: `lib/core/theme/app_colors.dart:3-27` defines the central palette, but Home and workflow screens introduce raw colors such as `#38291A`, `#96170D`, `#3B5311`, `#B91C1C`, `#10B981`, `#047857`, `#C5221F`, and several page-specific neutrals in `tab_beranda_admin.dart`, `tab_beranda_monitoring.dart`, `monitoring_list_screen.dart`, and `laporan_preview_screen.dart`. A source scan found 93 `Color(0x...)` occurrences in `lib/` and multiple raw text/progress color combinations. The Monitoring CTA at `tab_beranda_monitoring.dart:169-174` adds a gradient without a written hierarchy reason.
- Why it is slop: status colors may be legitimate, but they are not expressed as a small semantic system. The same red family currently means brand, CTA, progress, warning, and unread state, while near-duplicate green and red values appear beside the declared tokens.
- Fix proposal: centralize semantic aliases such as `brandPrimary`, `actionPrimary`, `statusAttention`, `statusSuccess`, and `notificationUnread`. Keep a gradient only if its role is written down, and make the active palette and status exceptions explicit.

### AS-009 - MEDIUM - Typography and radius tokens are bypassed across the role homes

- Rules: R-06, R-11, R-31.
- Evidence: `lib/core/theme/app_text_styles.dart:4-135` and `lib/core/theme/app_theme.dart:23-105` define shared typography, card, button, and input tokens, but the role homes use many local `TextStyle` values and local radii, for example `tab_beranda_admin.dart:145-187,215-225,289-366`, `tab_beranda.dart:103-113,347-361`, and `tab_beranda_monitoring.dart:45-60,120-152,196-210`. The repository uses `BorderRadius.circular` values from 2 through 24, including 10, 14, 20, and 24 outside the documented 8/12/16 rhythm.
- Why it is slop: the same content roles receive different type sizes, weights, line heights, and corner treatment depending on which role renders them. The token system exists but is not the source of truth.
- Fix proposal: map common text and surface roles to `AppTextStyles` and a small radius scale. Keep exceptions only when their hierarchy purpose is documented in the design contract.
### AS-010 - MEDIUM - Shadow and elevation treatments are repeated without a documented hierarchy reason

- Rule: R-12.
- Evidence: `lib/features/monitoring/presentation/widgets/tab_beranda_monitoring.dart:81-93` adds a shadow to the profile card, `:167-182` adds another to the primary CTA, and `:251-265` adds another to each active assignment card. `lib/features/monitoring/presentation/screens/laporan_preview_screen.dart:128-135` adds a large document shadow while the global `CardTheme` in `lib/core/theme/app_theme.dart:23-30` is otherwise flat.
- Why it is slop: multiple surfaces float at once, so elevation no longer communicates which object is primary. The result is a generic soft-card treatment rather than a deliberate hierarchy.
- Fix proposal: reserve elevation for the one or two surfaces that need to lift above the page, use borders or flat surfaces elsewhere, and record the hierarchy reason in the design contract.

### AS-011 - LOW - Role navigation shells duplicate styling decisions instead of sharing one component contract

- Rules: R-20, R-31, C-1.
- Evidence: `lib/features/dashboard/presentation/screens/dashboard_screen.dart:31-70`, `lib/features/dashboard/presentation/screens/admin_main_screen.dart:42-80`, and `lib/features/monitoring/presentation/screens/monitoring_main_screen.dart:38-62` independently define selected/unselected colors, icon families, elevation, and item labels. The item counts differ legitimately by role, but the visual contract is not shared.
- Why it is slop: role-specific navigation is correct product behavior, yet duplicated shell styling makes the app look like three unrelated products and makes each later fix drift again.
- Fix proposal: keep the role-specific destination lists, but implement one role-aware navigation component for safe area, height, typography, icon weight, active state, and badge semantics.

### AS-012 - HIGH - The mandatory runtime verification gate cannot be completed in the current environment

- Rule: R-35.
- Evidence: `flutter --version` and `flutter analyze --no-fatal-infos` could not run because `flutter` is not recognized on PATH. No click-through or rendered screenshot verification has been recorded for this audit pass.
- Why it is slop: a UI audit that is never run cannot prove there is no overflow, clipped text, dead control, or state failure on the target device.
- Fix proposal: run the app and the full role click-through in a Flutter-enabled environment before any delivery claim. Record the device viewport, build/analyze result, console result, and each navigation/state check.

### AS-013 - LOW - Design direction metadata is incomplete for the anti-slop delivery gate

- Rules: R-37, R-31, C-1.
- Evidence: `docs/design/mobile_application_mockup/rustic_authority/DESIGN.md` documents palette and an 8px spacing rhythm, but a scan found no explicit `ENERGY`, `RHYTHM`, `MOTION`, or `Design Read` declaration and no one-line reason for several screen-level deviations such as the Admin authority header and Perwaskim gradient CTA.
- Why it is slop: the visual choices can be intentional, but their intent is not recorded in a way that can be checked consistently across roles.
- Fix proposal: add a short design-read block with the three dials and one-line reasons for the header variants, role hierarchy, gradient use, accent allocation, and motion policy.
